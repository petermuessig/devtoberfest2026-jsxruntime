UI5 Views,
Reimagined

Type-Safe TSX for a Modern Dev Experience

ready to use   incubation   @ui5-community/jsx-runtime

Welcome to the session! Today we're going to look at something experimental and exciting: writing UI5 views with TypeScript JSX — the same TSX syntax you may know from React, but without React. Just UI5, but with full type safety in the view layer. Let me start with a question.
"You shouldn't have to choose between
declarative and type-safe."

— the question that started this project

In UI5 today you have a choice: XMLViews are beautifully declarative — they look like UI code. But they have zero TypeScript checking. If you mistype a property name, you find out at runtime. On the other hand, you can write views in JavaScript/TypeScript directly (new Button({...})) — but that's imperative and hard to read. There was no middle ground. Until now.
The status quo

Two worlds, neither complete

XMLView today

  • Declarative, readable
  • Familiar to UI5 devs
  • No TypeScript checking
  • No autocomplete on props
  • Typos found at runtime
  • No refactoring support

JS/TS Views today

  • Fully typed
  • IDE autocomplete
  • Imperative — hard to read
  • new Button({text:"…"})
  • Deeply nested = painful
  • Hard to see the component tree

We want the readability of XML with the type safety of TypeScript.

XMLViews look like UI. You can read them top to bottom and see the component tree. But TypeScript doesn't understand them at all. JS/TS views are fully typed — but they look like imperative configuration code. Deeply nested structures become very hard to read. What if we could have both?
JSX primer

What is JSX / TSX?

JSX — XML-like syntax that compiles to function calls

TSX — JSX + TypeScript = fully typed view code

Not a framework. Not a runtime library. A syntax transform. 


// What you write:
<Button text="Order" press=".onOrder" />

// What Babel compiles it to:
_jsx(Button, { text: "Order",
               press: ".onOrder" })

// What our runtime does:
new Button({ text: "Order",
             press: ".onOrder" })
The JSX/TSX transform is just syntactic sugar over constructor calls. No framework. No VDOM. No reconciler.
JSX was invented by the React team but it's not React-specific. It's a syntax extension that any compiler can support. TypeScript has had JSX support since day one. The key insight: JSX compiles to function calls. React uses _jsx(Component, props) to create VDOM nodes. We use a different runtime that calls new Control(props) instead. So the TypeScript compiler checks your props against the UI5 control types — same compiler, different runtime target.
Motivation

We've done this before

Remember when TypeScript came to UI5 controllers? Same story.

TypeScript in UI5 (controllers)

  • Type-checked event handlers
  • Autocomplete on models, APIs
  • Refactoring across files
  • Catch bugs at compile time

TSX in UI5 (views)

  • Type-checked control props
  • Autocomplete on every attr.
  • Refactoring across views
  • Catch typos at compile time

TSX extends the type-safety story from controllers to views.

When TypeScript came to UI5, the value proposition was exactly: type safety and IDE/tooling out of the box — in the controller layer. That story was compelling enough that it's now the recommended way to write UI5. TSX is the same story, one layer up: now your views get the same treatment. And because the rest — models, controllers, bindings, i18n — stays exactly the same, you can adopt it incrementally.
Architecture

How it works in UI5

🔷
TypeScript compiler  — checks $XSettings types: prop typos, wrong types, missing props
↓
⚙️
Babel @babel/plugin-transform-react-jsx v7  — <Button/> → _jsx(Button, {}) · via ui5-tooling-transpile
↓
🟢
JSX runtime @ui5-community/jsx-runtime  — jsx(Button, props) → new Button(props), resolves aggregations & directives

No React. No VDOM. No reconciler. Reactivity = UI5 data binding (unchanged).

Three layers: 1. TypeScript compiler: checks your props at COMPILE time against the UI5 control type definitions. 2. Babel transform: turns JSX syntax into function calls. This happens at build/serve time. 3. The runtime shim: tiny library, ~100 lines. It receives the function call and calls new Control(). It also handles aggregations, binding strings, and structural directives like and . UI5 data binding is completely unchanged. Bindings still flow through the model layer. The runtime only touches object construction.
Benefits

What you get

  • Per-control prop typing against $XSettings
  • IDE autocomplete on every attribute
  • Rename / go-to-definition on views
  • Catch typos like ttle= at compile time
  • Native JS loops & conditionals in views
  • All bindings unchanged:
    "{i18n>key}"
  • All aggregations unchanged
  • All controllers unchanged
  • All routing/i18n unchanged
  • Full coexistence with XMLViews

// TypeScript catches this immediately — in your editor, before you run anything:
<Column ttle="Book" />
//       ^^^^ TS2322: Type '{ ttle: string }' is not assignable to type 'Column$Settings'
This is the headline benefit: the same TypeScript that already checks your controller code now also checks your view code. You get autocomplete, go-to-definition, rename across views and controllers. And crucially: everything else stays the same. If you know UI5 bindings and controllers, you already know 90% of what you need. The only new thing is the view syntax.
Capabilities

What you can do

Controls & aggregations


// Default aggregation = children
<Panel>
  <Button text="Click" />
</Panel>

// Named aggregation = prop
<Table columns={[
  <Column />, <Column />
]}>

Bindings & events


// String binding (same as XML)
<Text text="{i18n>hello}" />

// Object binding (formatter)
<Text text={{ path, formatter }} />

// Expression binding
state="{= ${stock} >= 20 ? 'Success' : 'Error' }"

// Dot-handler event
press=".onSelect"
// Or typed function ref
press={(e) => console.log(e)}
Structural directives: <For> · <If>    Nested views · Coexistence with XML
Let me give you a quick overview of the full surface area. Controls: each imported class IS the JSX tag. default aggregation = children, named aggregations = props. Bindings: string form works exactly like XML — {"path"} syntax, i18n>, expression bindings, all of it. Object form { path, formatter } for TypeScript formatters. Both work. Events: dot-handler string ".onSelect" resolves against the controller. Function ref for inline typed handlers. Structural directives For and If — we'll use those in the demo. Full coexistence: TSX views can embed XML views and vice versa.
Directives

Structural directives: <For> & <If>

<For> — bound list


import { For } from "ui5/community/jsx/runtime/jsx-runtime";

// Explicit: each= + factory child
<For each={{ path: "/Books" }}>
  {() => (
    <StandardListItem title="{title}" />
  )}
</For>

// Implicit: items= on the parent
<List items={{ path: "/Books" }}>
  <StandardListItem title="{title}" />
</List>

// String binding
<List items="{/Books}">
  <StandardListItem title="{title}" />
</List>

<If> — conditional


import { If } from "ui5/community/jsx/runtime/jsx-runtime";

// Literal: resolved at construction time
<If condition={true}>
  <Text text="Always here" />
</If>

<If condition={false}>
  <Text text="Never here (dropped)" />
</If>

// Bound: adds visible binding on children
<If condition={{ path: "/showDetails" }}>
  <FlexBox id="details">...</FlexBox>
</If>
Two structural directives ship with the runtime. For: renders a bound list. Three spellings are equivalent — use the one that reads best to you. The factory function is the row template. The runtime calls control.bindAggregation() under the hood. If: two modes. Literal condition is resolved at construction time — child is either included or dropped, no binding overhead. Bound condition adds a visible=true/false binding to each child at runtime. Either way, no extra wrapper DOM element.

Key concepts

The TSX view anatomy


import View from "sap/ui/core/mvc/View";
import type Control from "sap/ui/core/Control";
import Page from "sap/m/Page";

/** @alias sap.codejam.view.App */      // ① AMD module name (explicit)
export default class AppView extends View {
  getAutoPrefixId(): boolean {          // ② scopes IDs — prevents duplicate ID warnings
    return true;
  }
  getControllerModuleName(): string {   // ③ wire a separate *.controller.ts
    return "sap/codejam/controller/App";
  }
  createContent(): Control {            // ④ the view — returns the root control
    return <Page title="{i18n>Bookshop}" />;
  }
}

Reference in manifest.json: "viewName": "module:sap/codejam/view/App"  module: prefix required

Four things to remember for every TSX view: 1. @alias JSDoc — pins the explicit dotted AMD module name (e.g. sap.codejam.view.App → module:sap/codejam/view/App) 2. getAutoPrefixId() — scopes all control IDs to this view instance (prevents duplicate ID warnings when the view is used more than once; XMLViews do this implicitly) 3. getControllerModuleName() — wires the separate controller, same as controllerName= in XML 4. createContent() — returns the root control, JSX inside In manifest.json, reference the view with the module: prefix + slash path. Without module:, UI5 looks for an XMLView and you get a 404.
Honest limitations

What's not there yet

Current gaps

  • HTML intrinsics (<div>, <span>) are missing
  • No Flex (UI5 flexibility) out of the box

Roadmap

  • HTML renderer plugin in progress
  • Flex via same pre-render hooks as XML (ChildrenProcessor / Scope SPI)
  • Stabilisation & docs polish
Ready to use today. Official release will be mostly API-compatible — only runtime internals may change. Your view code won't need rewriting.
Let me be honest about what's not there yet. HTML intrinsics: you can write
in a TSX view and TypeScript won't complain. But at runtime, the runtime doesn't know how to render a native HTML element yet. A plugin to handle that is in progress. Flex/UI5 flexibility: the runtime exposes the same SPI hooks as XMLViews — ChildrenProcessor and Scope. So Flex support is achievable via the same mechanism XML uses. It hasn't been wired up yet. On the "experimental" label: use it. It works today. The official release will be mostly API-compatible — only the runtime internals may change, not the view code you write. So you won't have to rewrite your App.tsx when it goes stable.

Quick reference

Setup in 4 steps

1. Install


npm i @ui5-community/jsx-runtime
npm i -D \
  @babel/plugin-transform-react-jsx@^7
npm i -D ui5-tooling-transpile@^3.12

2. tsconfig.json


{
  "compilerOptions": {
    "jsx": "react-jsx",
    "jsxImportSource":
      "ui5/community/jsx/runtime",
    "types": [
      "@openui5/types",
      "@ui5-community/jsx-runtime"
    ]
  }
}

3. ui5.yaml (key parts)


builder:
  settings:
    includeDependency: [ui5.community.jsx.runtime]
  customTasks:
    - name: ui5-tooling-transpile-task
      configuration:
        transformJSX:
          runtime: automatic
          importSource: "ui5/community/jsx/runtime"

4. index.html + manifest.json


// index.html resourceroots:
"ui5.community.jsx.runtime":
  "./resources/ui5/community/jsx/runtime/"

// manifest.json libs:
"ui5.community.jsx.runtime": {}
If you want to try this yourself after today, here's the four-step setup cheatsheet. The full details are in WALKTHROUGH.md in the session repo.
Gotchas

Things to watch out for

❶ jsxImportSource: AMD namespace, not the npm package name
✅ "ui5/community/jsx/runtime"   ✗ "@ui5-community/jsx-runtime"
❷ module: prefix in manifest rootView/routing
✅ "module:sap/codejam/view/App"   ✗ "sap.codejam.view.App"
❸ Add resource-roots for the runtime in index.html
Without it: 404 loading ui5/community/jsx/runtime/jsx-runtime.js
❹ getAutoPrefixId(): true on every view
Without it: control IDs are global — duplicate ID warnings when view is instantiated >1×
Four gotchas that catch almost everyone the first time: 1. jsxImportSource is the AMD/ES module path, not the npm package name. Use the slash-form namespace. This is the #1 confusing thing. 2. In manifest.json, TSX views need the module: prefix. XML views use a dotted class name. Without module:, UI5 tries to load an XMLView and fails. 3. Resource roots: without this entry in index.html, the browser can't load the runtime at all. 4. getAutoPrefixId: XMLViews do this automatically. TSX views don't. Without it, control IDs are global and you'll get duplicate ID warnings if the view is instantiated more than once. byId() still works — it's about ID scoping, not lookup.
